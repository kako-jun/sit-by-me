# Sit by Me 戦闘背景

**画像の保存形式（#68決定、2026-10-19）**: imagegenの出力（PNG）→切り出し→**WebP（非可逆・品質85・アルファ保持）**にして正本パスへ保存する（`magick in.png -quality 85 out.webp`、または `verification/characters/tools/key_*.py` が直接WebPで出す）。PNGは残さない（name-name のTUIは WebP のみデコードできる）。実寸（不変）・アルファ（`magick in.png -alpha extract` と変換後WebPの同コマンドを `compare -metric AE` で比べAE=0）の検査はWebPで行う。寸法ゲートの基準（1920×1080等）は変えない。

失敗の来歴（完全prompt・参照・実寸/検査結果・判定理由）はIssueまたはレビュー文書に記録し、失敗画像はリバートする（バイナリを別置き場に保存しない）。

劇・屋外を含む戦闘用背景を扱う。**劇の背景: 旧採用の BG005.webp は没（kako-jun 2026-10-21。削除済み）。劇の背景の正本は現時点で未定。方針（kako-jun 2026-10-21）: BG009（履歴 1bb09d0 の候補。汚いので正本にせず復元しない）は舞台の構成の方向性のみ採用（緑の幕・手描きの青白い雪山と赤い屋根の城の書き割り・段ボールの縁とマスキングテープのある木の舞台）。劇の戦闘背景は、採用した幼稚園室内（TRM-02）の舞台を参照に、TRM-02 の採用後に新規生成する（下の「該当MAP画像を参照に入れる」規定どおり）。TRM-02 の採用までは生成を停止する（推測で別の絵を当てない）。没の素材（BG005 の要素: えんじ色の幕・脚立・段ボール箱を含む）は参照にしない。**（採用状態は台帳のstatusで管理する。）通常のフィールド背景は `sit-field-background` を使う。

## 一意解釈ゲート（このスキルの全行より優先）

生成入力・検査には、参照画像パス、1920×1080座標、画面端、ピクセル数、個数、材料名、色名、または下記で定義した方向だけを使う。`少し`、`やや`、`広い`、`狭い`、`近い`、`遠い`、`自然`、`十分`、`明瞭`、`目立つ`、`適切`、`雰囲気`、`おおよそ`、`〜風`、`斜め`だけ、`奥行き`だけは実行語として禁止する。必要な条件をそれらだけで表している場合、座標・参照画像・数値へ変換できるまで生成を停止する。背景と地面の境界は、左端のy座標から右端のy座標を**40 logical pixels以上小さくする**場合だけ「左下から右上」と判定する。

床板、幕、書き割りを、見栄えのために直線・直交・等間隔・格子へ正規化してはならない。形・数・位置は参照画像または原文にあるものだけを使う。

## ミニチュア材料・道具の固定宣言

（劇の背景は上記のとおり、正本が決まるまで停止。以下の劇の材料指定は、正本が決まった後の参考。）劇の背景では「手作り舞台」「ミニチュア」だけで生成せず、床=`balsa wood` または `popsicle sticks` をクラフトナイフで切断、書き割り=`corrugated cardboard` と `matte poster paint`、幕=`felt` または `tissue paper`、固定=`masking tape`・PVA接着剤、土台=`foamboard` と露出段ボール断面を対象ごとに指定する。屋外背景は対応MAP原文と `sit-field-background` の対象別材料・加工法を使い、劇場床・幕・書き割りを追加しない。実物素材やCG均一面で代替しない。指定した材料・切断面・テープ・接着剤・土台断面のうち三つ以上を原寸の証拠座標で確認できなければ `failed` として記録し、採用候補へ進めない。

開始前に `docs/content-registry.md` から対象の戦闘・MAP IDを確定し、対象MAPの原文、`docs/art-direction.md`、対応する戦闘レイアウトJSONのキャラ・敵・UIの安全領域を読む。劇の場合は `docs/roadmap.md` の劇背景決定も読むが、その BG005 の決定は没（2026-10-21）で、劇の背景の正本は未定のため生成は停止する。

## 絶対ゲート: 参照MAPと戦闘面の角度

生成前に、戦闘の場所に対応するフィールドMAPを原文台帳から確定し、**実際のMAP画像を imagegen の参照画像として必ず入力する。** 劇なら該当する幼稚園／遊戯室MAPを両方確認し、屋外なら該当する屋外MAPを全て確認する。どの画像を建築・材料・幕・室内位置関係・地面のどれの根拠に使うかを生成記録に残す。文章だけで場所を再現してはならない。対応MAPが無い、原文と画像が矛盾する、または参照画像を入力できない場合は生成を停止する。

`assets/images/battle-backgrounds/BG001.webp`（旧bg-a）をカメラ参照画像として入力する（旧 BG005 は没で削除済みのため入力しない）。地面と背景の接する線について、右端のy座標を左端のy座標より40 logical pixels以上小さくする。真上見下ろし、正面カメラ、水平な地面・背景境界を出力しない。**左右反転（ミラー）で向きを直すことは禁止**（kako-jun「左右反転なんてゆるさない。絶対にちゃんとした視点から一発でつくれるようにしろ」2026-10-21）。正しい視点から一発で生成できるよう、プロンプトとガイド図（平行投影の灰色の線図。BG010 は scratchpad の mkguide-geki.py）で保証する。（取り消し記録 2026-10-21: 先に入れた「視点を低くしてよい・地面の割合の緩和」は kako-jun『視点を低くはちがうか』で取り下げ。Issue #9 の「地面約9割」を維持する。）ジオラマの外が白くなる・壁部分が多すぎる場合は、背景を足さず、カメラをもっとジオラマに寄せて、上と左右は見切れてよい（kako-jun『だから寄ればいい。ダンボールの端が上と左右は見切れてもいい』）。。）**「斜め」の定義（kako-jun 2026-10-21）: 斜め＝カメラが、戦闘しているフィールドだけの小さな卓上ジオラマを、高い位置から少し斜め（ヨー）に見下ろす結果として、斜めの平行線が出る。物（幕・書き割り・背景）自体を傾けない。原文は「すこし斜めしてんから見下ろせ」で、「斜め上から」と読んだ。****斜めの目的（kako-jun 2026-10-21、逐語）:「斜めから見下ろすから床の模様や水平線などもすこしだけ斜めになることで、戦闘画面がフィールドとかぶった印象にならないことを狙っているのだ」。斜めの目的＝戦闘画面がフィールド（見下ろしのMAP）とかぶった印象にならないようにする。斜め上から見下ろす結果として、床の模様・水平線（遠景の線）が少しだけ斜めになる。** 「少しだけ」＝ヨーを小さくする（角度で指定。大きく傾けない）。 上の40 logical pixelsの測定は検査として維持する（カメラの結果として右端が左端より高くなっているかを測る）。検査には上限も設ける: 過度な斜めは「少しだけ」に反するため、右端と左端の差が画像高さの約10%以内を目安にする（検査の目安で、prompt には書かない）。**フィールド背景との区別**: フィールドMAPの見下ろしは真上寄りの斜め俯瞰（北=上、ヨーなし。sit-field-background）で、戦闘背景はそれとは別の向き（少しヨーを付けた視点）にして、戦闘画面がフィールドとかぶった印象にならないようにする。

**反復する床板線・轍・溝・タイル線は必須ではない。** それらは場所の原文またはユーザーが要求した場合だけ描く。角度の根拠を線の反復で代用してはならない。

生成後、原寸で次の全項目を二択確認する。ひとつでも `いいえ` なら `failed` として記録し、採用候補・後工程へ進めない。

1. 対応フィールドMAPを実際に参照画像として渡したか。
2. 地面と背景の接する奥端が、左下から右上へ上がる画面方向になっているか（右端が左端より明確に高いか）。**原寸で左端と右端の境界のy座標を測り、右端が左端より40 logical pixels以上小さい（高い）ことを数値で確認して記録する。目視だけで通さない**（劇の背景の候補 BG009 は、この規約に違反していたが検査で効いていなかった。kako-jun 2026-10-21。規約は既存の「一意解釈ゲート」・絶対ゲートの40 logical pixels・「水平な地面・背景境界を出力しない」と同じもので、ここに重複して別の規約を足したものではない）。
2b. **壁部分（幕＋書き割り＋書き割りの奥）の最大yが画像高さの約1割（約94px、1672×941）以内か、床が約9割か**を、原寸で測って記録する（kako-jun の本旨「背景の壁部分が多すぎる」。2026-10-21）。
2c. **平行性**（Issue #9「キャビネット図のような斜投影」＝平行投影。透視の収束・扇状の線は不可。kako-jun「床の線が上の線と平行にみえない」2026-10-21）: 生成後に原寸で、書き割りの足元の線・床板の継ぎ目（数本）・手前の段ボール縁の傾き（px/px）を測り、最大と最小の差が書き割り足元の傾きの約20%以内かを確認して記録する。
3. 地面の角度を、不要な反復線の追加で偽装していないか。
4. 参照MAPの建築・材料・場所の手がかりと矛盾していないか。

## 背景契約

- 横長16:9（1920×1080論理座標）にする。人物、読める文字、ロゴ、透かしは入れない。
- 味方、敵、十字コマンド、メッセージ窓の占有矩形は対象戦闘のレイアウトJSONの値をそのまま読み、その矩形に背景物を置かない。
- 劇の背景は、正本が決まるまで生成しない（BG005 は没）。以下は旧記述（履歴）: 劇を対象にするときだけ、緑の幕、子供が手描きした段ボールの雪山と城の書き割り、木の床を描く。舞台袖の脚立・小道具はレイアウトJSONの安全矩形の外だけに置く。
- 屋外を対象にするときは、建築・地面・天候・時刻を対応MAP原文と参照MAP画像からだけ取る。劇の幕、書き割り、舞台床を追加しない。

## 運用

生成前に完全prompt、対応MAP原文、実参照画像と用途、安全矩形の出典を `sit-artifact-redteam` のpromptレビューへ渡す。旧候補と現行契約の矛盾を隠して建築の根拠にしない。利用可能な `imagegen` スキルと組み込み `image_gen` を使う。実ファイルが1920×1080か測定し、原寸上の境界両端座標と材料の証拠座標を記録する。論理座標や16:9比率だけでは寸法を証明できない。完全prompt・参照・測定値・結果を記録し、独立生画像レビュー後に実戦闘へ重ねる。保存禁止は採用候補化の禁止を意味し、失敗来歴を捨てる指示ではない。

1. 戦闘背景IDは#68の対応台帳で確定し、正本を `assets/images/battle-backgrounds/BGxxx.webp`へ直接上書き保存する（`candidates/` や版suffixは使わない）。合格ならコミット、不合格・不採用は `git restore <path>`（未追跡の新規ファイルは即削除）でリバートし、不採用・失敗画像は置き場に残さない。**使う可能性のあるテイクは、次を生成する前にコミットする**（未コミットの新規ファイルは次の上書きで消える）。`git add` は名指し。採用状態は置き場でなく台帳のstatusで管理する。 上書きで既存の採用画像を置き換える場合は、現行をコミット済みか先に確認する。
2. 生成後、16:9比率、アクスタ／敵／UIの余白、幕・書き割りの舞台性、文字なしを確認する。
3. 実際の戦闘画面に重ね、ライブ表示で視認性を確認してから採用を判断する。

共通（#68運用）: 合格済みの正本を上書きする前に、現行がコミット済みか確認する。不合格テイクをコミット済みにしてしまった場合は `git revert <commit>`、または `git checkout <旧commit> -- <path>` で戻す。
