# Sit by Me NPC配置・セリフ作成

NPCを「シナリオ地点 → MAP → NPC → 出現条件 → セリフ」で結ぶ。**1人に1行だけ作って終わりにせず、そのNPCが登場する全ての場面に、その時の状況に合う行を作る。** 台帳が正本。地形やマスクが未確定でも、位置は仮置きとして会話作りを止めない。

## 先に読む資料

着手前に、以下を読み、矛盾する場合は確定台帳・決定・ユーザーの最新指示を優先する。

1. `docs/INDEX.md` と `docs/content-registry.md` — 正本と台帳構造を特定する。
2. `docs/story.md` と `docs/timeline.md` — 出来事、人物関係、時期を確認する。
3. `docs/scenario-registry.md` — `E...` のイベント地点と `N-ERA-...-MAP` の探索地点を区別する。
4. `docs/decisions.md`、`docs/ledger/決定.yaml`、`docs/ledger/未決.yaml` — 配置禁止・例外・確定事項・未決を確認する。未決を確定扱いしない。
5. `docs/ledger/人物.yaml`、`docs/ledger/人物形態.yaml` — NPC候補、人物の芯、外見・年齢・役割を確認する。
6. `docs/ledger/MAP.yaml`、`docs/ledger/MAP仕様.yaml`、`docs/ledger/MAP契約.yaml` — MAP名・用途・接続の根拠を確認する。接続未確定の道案内を作らない。
7. `docs/ledger/NPC配置.yaml`、`docs/ledger/NPCセリフ.yaml` — 既存行、ID、場面差分、重複を確認する。
8. `docs/systems.md` — 店・道具・ゲーム上の説明が必要な時だけ読む。
9. Issue #246（全体整理・配置案・kako-junの指示）、#236（配置とセリフの背景）、#180（NPC候補・形態の採用記録） — 関連する最新コメントを確認する。コメントの提案を、採用済みの決定と取り違えない。

資料が見つからないときは `rg --files` で所在を探す。Issueの記録や台帳にない物語設定・人物の過去を補作しない。

## 作成手順

1. 作業対象のIssueに、対象範囲・参照する資料・台帳への追記内容・独立レビューを先に記録する。
2. シナリオ地点とMAPを列挙し、イベント会話と探索中の会話を分ける。MAPごとの配置案は既存の持ち場案を起点にする。
3. NPC候補を人物の役割・時代・配置制約と照合する。子供時代のフィールドモブは子供から、大人時代のフィールドモブは老人から選ぶ。固有の物語人物やイベント役はモブ候補と混ぜない。明示されたNPC不在の場所・例外を守る。
4. 各NPCについて、配置表の全出現行を抽出し、各行に対応する会話行があるか確認する。探索用の包括配置（例: `N-ERA-ALL-MAP`）と時代別会話のように粒度が違う場合は、その対応関係を備考で明記する。
5. 台詞は、その人物の「人物の芯」や見た目・持ち物、役割から個性を出し、さらにその時期・場所の状況に反応させる。別場面の台詞は、MAP名だけ差し替えた同文にせず、話題・観察・助言のいずれかを場面に合わせて変える。
6. 方言は作品共通の声として扱う。性別だけを根拠に口調を決めつけず、性別や話し方が正本で明示されている場合に限り反映する。個性は語尾のステレオタイプではなく、話題の選び方・反応・行動に出す。固有の口癖は根拠がある時だけ使う。
7. NPC配置・NPCセリフの既存スキーマを使い、台詞と位置・発火条件は未確定なら `仮稿` とする。位置や条件は地形・マスクの未確定を理由に空欄で放置せず、後から直せる仮案を記す。台帳の形式を変える必要がありそうでも、ユーザーがコード実装を求めていない限りコードを変更しない。
8. 台詞を書いた本人とは別のレビュー担当に、完成した配置・セリフ表と参照資料を渡し、独立レビューを依頼する。次の観点を、人物ID・配置ID・セリフIDを挙げて確認してもらう。
   - 候補NPC・配置行に対するセリフの欠落、場面条件のずれ、時代違い
   - 子供／老人の時代制約、NPCを置かない場所、固有人物とモブの混同
   - 人物の芯が台詞に出ているか、同一人物の別場面で反応が変わるか、本文の使い回しがないか
   - ストーリー・MAP・システムの事実誤認、接続や未決事項の断定、根拠のない背景・口癖・性別口調
   - 方言の読みやすさ、子供／老人や人物間の声の区別。方言を理由に性別差を機械的に付けない
9. 指摘のうち欠落・事実誤認・制約違反を修正する。判断が要る指摘は未決として記録し、勝手に採用しない。
10. 台帳を再生成・検証し、件数とカバレッジをIssueに記録する。通常は `uv run python3 scripts/build_ledger.py build` と `git diff --check` を使う。台帳作業だけでフルテストを追加・実行しない。ゲーム上の会話確認は実装接続後に別途行う。

## 完了時に報告すること

- 作成した配置数・セリフ数・対象NPC数
- 配置行に対するセリフの未対応数と、包括条件など意図した差分
- 複数場面に出るNPCの場面差分を確認した結果
- 独立レビュー担当、指摘数、反映または未決にした項目
- 台帳検証の結果と、ゲーム実機で未確認の範囲

全件が「仮稿」の場合は、監修・実機確認済みと表現しない。
