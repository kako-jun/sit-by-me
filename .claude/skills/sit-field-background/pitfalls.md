# ハマり所と対処（症状 → 原因 → 対処）

体内17枚の制作・マスク化・red-team（2026-10-22〜23、Issue #142）で出た手戻りを、**エリア共通**の形にした。工程番号は `SKILL.md` の12工程。体内の個別の数値・経緯は `body-appendix.md`。新しい学びは末尾の該当表に足す。

## A. kako-jun に途中で直された（着手前の確認票で防ぐ）

## B. 画像生成（codex）

| 症状 | 原因 | 対処 |
|---|---|---|
| 画像が保存されない（返却に保存パスが無い／`out/` が空）。体内で5回中3回 | codex の保存失敗 | codex.log の `session id:` と**一致する** `［ホーム相対パス省略］/generated_images/<セッションID>/` から**無加工で**コピー。ID不一致なら使わない。回収後に実寸・sha256 を記録 |
| `codex exec --full-auto` で生成できない／動かない | 当環境で無効 | `codex exec --skip-git-repo-check -s workspace-write -i ref1.png -i ref2.png < send.txt` |
| 並行エージェントで codex が重複起動、別担当の prompt が走った | scratchpad の共有ファイル名（`runall.sh`・`send.txt`・`ref1.png`） | ファイル名とディレクトリを MAP・担当ごとに固有にする（`run-bdy07.sh`・`bdy07-send.txt`・`bdy07-ref1.png`、`bdyNNop/`） |
| 参照が古い（旧版の画像を参照に渡した） | コピー元が古い、または別ファイル | 現行ファイルをコピーして**渡す前に sha256 を照合**する |
| 装飾込み1回生成で幾何が崩れる（床IoU 0.30〜0.78） | **様式参照画像**（参照3枚目）が幾何を崩す | 参照は2枚（clean 割付図＋材料見本）だけ。様式は文章で伝える（床IoUは 0.83〜0.95 に回復。経緯は body-appendix.md） |
| 細い通路で床が痩せる（約7割。床IoU 0.686） | 壁を太く描かれ、床を食う | 壁は床の外側の細く低い帯1本（幅約12px）。毛糸は床の幅に含めない。床の幅は壁の内側基準で指定（実際の床は10〜20%細くなる前提） |
| 禁止した物（花・雲）が出る／避けさせたい形が描かれる | 禁止語を書くと逆に誘発される | 肯定形で、使ってよい物だけを列挙。自作部分に禁止語が出たら停止する機械検査（`leak_check`） |
| 原文の語（『分岐室』『洞窟口』『水の精霊』）が絵の指示と誤読された | 原文束の語に引かれる | 本文に『この MAP の部屋は1つの袋』『床と地形に人物・精霊・炎・水の絵は無い』等を肯定形で1文足す。部屋名は絵に描かせず『丸い床』と呼ぶ。臓器名は送信文3行目に入れない |
| 赤い折り紙が6枚にならない（5枚が最多、模型の外・机に出る） | 数が守られない | 『Exactly six … no seventh』『数えて6枚』『All six lie on the terrain faces inside the model』を強め、置き場を地形上と明示。出ても欠陥として記録し、採否は目視。定数アクセントは多めに数えさせる |
| 返却寸法が 1672×941（1920×1080 でない） | 画像ツールの仕様 | 16:9 の 1672×941 は許容。チェッカーは倍率 幅/1920 を自動判定 |
| 1672×940（1px低い）が返る（BDY-13） | 同上 | 他寸法は不合格・リサイズ禁止が原則。**kako-jun の例外承認**を得て、台帳・採用記録・register・red-team に記録（体内 BDY-13 は承認済み） |
| prompt が長すぎる | 文字数上限（BDY-04 は 30,000 字以下に収めた） | 無関係な原文行は slim（対象行と接続相手の行は残す）、座標の二重併記を減らす |
| 原文束を最後に置くと不安／先頭に置くと形の指示が薄れる | 順序の効き | 台帳原文ゲートは添付を要求するだけで順序は不問。迷路・部屋の MAP は『wrapper → WHAT TO DRAW → REFERENCE → SOURCE TEXT』で SOURCE の末尾に終端行を置いてよい |
| 迷路など複雑な形が簡略化される | 文章だけでは一意に伝わらない | ステンシル宣言（参照1の cream は床のステンシル）、格子の式、全通路の列挙、ランドマーク、本数・T字・行き止まりの数を肯定形で。再生成は最大2回まで許可を取る |

## C. チェッカーと目視

| 症状 | 原因 | 対処 |
|---|---|---|
| 机と縁の色が近い（薄い木目の机）で机・縁・通路が誤判定（BDY-15〜17） | 4層の色分離が前提 | FAIL は重ね画像と原寸クロップで目視。誤判定なら採否に影響させず記録する |
| 床色を誤推定して床IoU=0（BDY-07。黄土色と誤認） | `estimate_floor_color` が失敗 | チェッカーの床色推定を疑う。実画像の帯の位置を目視。床色を `--floor-color` 等で指定できるようにするのが次の改善（tools/README.md） |

## D. 文書・Git・運用

| 症状 | 原因 | 対処 |
|---|---|---|
| 送信文の逐語照合が壊れた（`CUT_MARK` が見つからない等） | 台帳 docs の更新で原文行の位置・文言が変わった | docs を更新したら `--verify-send`・`--verify-bundle` を再実行。ビルダーは出力のたびに照合して不一致なら停止する。変更した docs の変更点を prompt に反映してから生成 |
| 別セッションの未コミット変更が同じファイルに混ざる（`docs/map-topology.md` 等の別領域・sit-enemy-sprite） | 共有作業コピー | コミット前に `git diff --cached` を確認。同ファイルの他領域は `git add -p` で当エリアのハンクだけステージ。`git stash`・`git add -A` 禁止 |
| モックを見せずに生成し却下 | 『機械検査OK』『レビュー可』を承認と取り違えた | モック提示ゲート。承認の記録（日付・sha256）が Issue に無いなら生成しない |
| 独立レビューが作成者と同じ担当だった／指摘修正後に再レビューしなかった | 運用の省略 | レビューは作成者でない担当。メイン以下のモデル（メインがSonnetなら sonnet 以下）。指摘は全件修正し必ず再レビュー（小さな修正でも） |
| red-team の証拠が主張だけで再現できない | 版が固定されていない | 検査した版を sha256 で固定し、原寸クロップ画像を証拠にする（sit-artifact-redteam） |
| 承認済みの逸脱が台帳に残らず次のレビューで再指摘 | 記録先が1か所 | 台帳・採用記録・register（または links）・red-team 報告・Issue に同じ文で記録 |
| 採用済みの旧版を作り直して劣化（BDY-02 の首の分岐が消えた） | 作り直しは常に改善とは限らない | 旧版を新版が採用されるまで残す。劣化したら『旧版でいいのでは』を kako-jun に聞く（実際に維持になった） |

## F. 斜め視点（寺町 TRM-02〜05。E1 幼稚園の学び、#144）

| 症状 | 原因 | 対処 |
|---|---|---|
| 丸テーブルが真円になって「縦横比OK」と書いた | 縦横比をその丸テーブルから決めていた（循環検証） | 縦横比の根拠が円なら円の真円度は証拠にならない。`oblique_register.py` は `circular`/`independent`/`quad-only` を分けて出す。独立検証は台帳・設計書の寸法、または別の既知の円 |
| 床板の水平・舞台前縁の水平を縦横比の証拠にした | 水平・垂直は縦横比に依らず、床の4点だけを検証する | `quad-only` と書く。縦横比の証拠にしない |
| 家具の穴埋めに凸包を使って床まで潰した | 凹んだ形（椅子の間の床）まで塞がる | 床色でない連結成分ごとに閉じて穴埋め→膨張。凸包は使わない |
| RGB の距離で床を切ったら影・木目で穴だらけ | RGB は明るさ・色相が混ざる | Lab のマハラノビス距離（床の芯の色から）。芯は枠を内側に削った領域＋色相で絞る |
| 絵から出入口（西壁の開口）を読んで出口にした | 絵の開口は設計書の扉位置ではない | 出口は設計書が正本。位置が TBD なら発明せず候補を並べて聞く。人が決めた位置を JSON に書く |
| 床の継ぎ目の垂直を合否に使った | 短くノイズが大きい（MAD 約5度） | 参考値にとどめ、判定は長い水平線（床板・舞台前縁）で行う |
| E2（TRM-02）で生成物の幾何保持を測ったが領域ずれが偽FAILだらけ | 小さい同形状の箱（椅子の列）・細い斜めの縁（西壁の戸口）は、モック自身を入力にしても隣と取り違えて8px超ずれる | 測定器を**モック自身で自己較正**し、自分でもずれる領域は『測定不能』として合否から除く（`oblique_e2_measure.py`）。基準値はモック自身の結果から決める |
| `codex exec` が「Argument list too long」を出した | image_gen の結果（base64）を1回のシェル引数で渡そうとした | 数秒後に codex が分割復号保存へ切り替えて成功する。生ログは数MBになるので先頭だけ残す（`oblique_e2_run.sh`が自動縮約）。保存物の本物確認は sha256 と `~/.codex/generated_images` の突き合わせ |
| 生成物が本物か（偽造PNGでないか）を画像を見ずに確認したい | ImageMagick 偽造は色数が少なく codex の出力フォルダに無い | sha256 が本ラン中に増えた `［ホーム相対パス省略］/generated_images/` の画像と一致・色数>5000・ログに magick/PIL 呼び出し0（`metrics.json` の provenance） |
| 4テイク並列で3分程度（codex）で全部返った | 参照2枚（clean＋素材見本）の編集 | 並列4で足りる。待ちは前景の `until` ループで（バックグラウンドの notification 待ちは不要） |
| E2: 幾何は全テイクで保たれたが局所だけずれた | 崩壊でなくテイクごとに別の場所（家具・戸口）がずれる | 4枚生成→輪郭一致＋領域ずれの測定で合格テイクを選別する方式が成立。ずれた領域が毎回同じなら、その箇所の文章固定を1点だけ足す |
| E2 round1: 幾何は保てたが kako-jun が全不合格（簡素・外周に木と草なし・層構造が消えた） | edit-prompt が物の名前と高さだけで見た目が無く、『足さない・消さない』が装飾まで禁じる読みになった。建物の外・台座・作業机の層の指示も無かった | 幾何固定と装飾を別軸に（prompt v3・decor_pool）。指定のない面は工作の装飾で十分に埋めさせ、層ごとの素材と固定を書く。測定にも装飾量・層・外周の木と草を入れる（幾何だけの合否だと簡素さを落とせない） |
| E2 round2: 装飾を許すと幾何が崩れた | A案=建物を描き直し全体が約20〜40px上へずれる。B案（元画像を様式参照で添付）=『構図コピー禁止』を無視して元画像の構図を再現（輪郭 Chamfer 1〜3px） | 様式参照に完成画像を渡す案は構図コピーになるので不可（体内マップの『様式参照なし』と同じ結論）。次の候補: 座標つきの固定文を足す／建物と外周を別生成して合成／領域ごとの位置合わせ。測定は元画像との Chamfer で構図コピーを検出する |
| 測定の合格基準を生成後に動かした | 較正や閾値を結果を見てから調整した | 基準は生成前に決めて報告に書く。測定の欠陥を直した場合は『較正前後で判定が変わった』と明記する |
| 外周の常緑樹が洋風（モミ・杉・クリスマスツリー型）になった | 『常緑樹』と書くと西洋の針葉樹に寄る。元の採用画像（参照）もそうだった | 寺町の木は松＋枯木に固定（kako-jun）。pool の `trees` に松の形（幹がうねる・横に張る枝・段状の房・盆栽的）と洋風の禁止を書く。測定の針葉判定は暗い緑〜青緑〜オリーブで松も拾う（ref の常緑樹量は洋風のためあくまで量の目安） |
| MAPごとに机の天面（作業机の材質・板目）が変わりそう | 層の look を MAP/テイクごとに自由に書かせていた | 机の天面・木の種類・台座の素材はエリア固定（`areas.<area>`）。pool/plan で上書きするとエラー。edit-prompt に『机の材質・色・板目の向きを変えない』と出し、測定は机の平均色（エリア値に対する ΔE≤15・テイク間≤8）と板目の向きで見る。基準は採用済み4枚の机の実測（ΔE 1.4〜3.5）から |
| 新エリアを作るとき机の材質を決めずに既存エリアを流用した | エリアごとの材質を発明しない決まり | `areas` に足す前に kako-jun と area_fixed（机・木・台座）を決める。決まるまで decor_pool を作らない（validate が area 未登録をエラーにする） |
| E2 round3: 座標で固定すると言っても建物全体の上ずれが残った（4枚中2枚で10〜14px） | 画素座標の文章だけでは生成の描き直しを完全には止められない（round2 A の約30px→1〜12pxに減った） | 座標節（COORDINATES）は有効だが十分ではない。次は生成の外で幾何を保証する案3（建物をクロップして生成→決定論の位置合わせ→外周と合成） |
| 家具の領域ずれが全テイクで同じ向きに大きく出た（table-small dy -30・round-table (+36,+28) 等） | 許可した装飾（机の上の積み木・机に寄せた椅子・棚の天板の小物）が箱の輪郭の外へ出て、輪郭帯の平行移動マッチが取り違える。自己較正（モック自身）は輪郭が疎なため検出できない | 装飾込みの画像では家具の領域ずれを合否に使わない（窓・戸口・壁を使う）か、箱の接地線で測る。基準を動かす場合は生成前に記録 |
| 全MAPで家具の領域ずれが上方向（dy -18〜-40）に出る | 脚のある机・小物つきの家具は接地線の輪郭が弱く、箱の上面の輪郭に取り違える（接地線で測っても同じ） | 家具の位置は参考扱い。合否と建物の位置の判断は窓・戸口・壁（`structure` 指標）で見る |
| 全MAPで建物全体が約4〜12px 上へずれる | 座標つき固定文でも描き直しの傾向は残る（窓は ±8px 内が多い） | 許容か平行移動で戻すかは kako-jun の目視後に決める。案3は不要（確定） |

2. 新しい節の最後、または直後に中核制約を再掲して統合する（競合する節は、中核制約を後ろに置く）。
3. `verify_prompt_reflects_ledger.rb` の `check_core_constraints` が通ること。新しい節が中核制約の語を否定していないか機械検査される。
4. 生成後の目視で『質感が工作の素材か』を採否の前に挙げる（`metrics.md` の目視確認項目）。

**D-prime の手順と合格基準（TRM-07 の素材感の実験。2026-11-11、Issue #191）**

- 実験の所見: A（見本シートのみ）・D（look の材質語を工作語化のみ）は素材感が不足、E（変換）は位置は保てるが素材が変わらない、C は素材感が強いが装飾が減る。**D-prime（D＋見本シート）が素材感・意匠保持・幾何で最良**（recall 0.832、chamfer 3.30）。kako-jun も『よい。まだミニチュアっぽくはないが』。以前の良い絵（2026-10-14、`22dc9511`）の鉄道模型の質感は、材料名の指定表（gates.md）から来ていたので復元した。
