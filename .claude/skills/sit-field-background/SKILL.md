**画像の保存形式（#68決定、2026-10-19）**: imagegenの出力（PNG）→切り出し→**WebP（非可逆・品質85・アルファ保持）**にして正本パスへ保存する（`magick in.png -quality 85 out.webp`、または `verification/characters/tools/key_*.py` が直接WebPで出す）。PNGは残さない（name-name のTUIは WebP のみデコードできる）。実寸（不変）・アルファ（`magick in.png -alpha extract` と変換後WebPの同コマンドを `compare -metric AE` で比べAE=0）の検査はWebPで行う。寸法ゲートの基準（1920×1080等）は変えない。 マスク・編集マップなど厳密な画素が要るものは**可逆WebP**（`-define webp:lossless=true`）で保存し、PNGは残さない。 MAPの既存PNG（fields/legacy・masks）はMAP改名PR（PR-M）でWebP化するまで現状のまま。

Sit by Me のフィールド背景を、手作りのミニチュアに見える一枚絵として作る。**エリアごとに同じ12工程**で進める。敵は `sit-enemy-sprite`、召喚獣は `sit-summon-sprite`、人物は `sit-character-sprite`、戦闘背景は `sit-battle-background` を使う。このスキルは**フィールド背景だけ**。

## 台帳の運用（絶対。台帳 = `docs/ledger/*.yaml` が情報の唯一のマスター。2026-10-24）

1. **決定は先に台帳へ**: kako-jun の決定・指示は、まず `決定.yaml`（逐語・出典つき。status に関係なく全件がプロンプトに入る）に書く。Issue は決定IDを参照するだけで、**Issue にだけ書かない**。Issue の決定候補の取りこぼしは `ruby scripts/audit_issue_decisions.rb` が検出する。
2. **必須キーと自由記述**: 表ごとの必須キーは `必須キー.yaml`。欠けている・『未決(要確認)』のMAPは `oblique_build.py` が起動しない（形・数値を発明しない。未決は `未決.yaml`）。決まりが表の列に収まらないときは、その行の `特徴(自由記述)` 欄にそのまま書く（プロンプトの FEATURES 節に入る。`verify_prompt_reflects_ledger.rb` が漏れを検出）。
3. **画像生成は、台帳整理の完了と kako-jun の再開指示があるまでしない**（現在は停止中）。
4. **生成画像は Claude は見ない**（見るのは kako-jun）。Claude が扱うのは、スクリプトの測定値（`oblique_e2_measure.py`）と台帳だけ。
5. **プロンプトの文面・寸法はコードに直書きしない**: 台帳の `プロンプト文面`・`描画定数` を直す（コードは `oblique_text.py` で読むだけ）。
6. 変更したら `ruby scripts/verify_ledger.rb`（スキーマ・外部キー・鮮度・コードと台帳の対応）と `ruby scripts/verify_prompt_reflects_ledger.rb` を通す。入口と表の一覧は [docs/INDEX.md](../../../docs/INDEX.md)。

## モック提示ゲート（絶対・最優先。このスキルの全行より優先）

kako-jun 指示（2026-10-22、逐語）: 『モックを見せずに作ることはスキルで禁止にしろ』。

1. **承認なしの画像生成は禁止。** imagegen を呼ぶ全て（試験生成・1枚だけの試作・並行生成を含む）の前に、対象エリア／グループの**全MAPのモック**（割付図・接続・各MAPの道の形と向き）を kako-jun に一度見せ、**明示の承認**を得る。『仮案だが機械検査OK』『レビューが可と言った』『試験だから1枚だけ』は理由にならない。
2. **見せ方**: 全MAPを1枚の一覧（体の配置・地図の配置に沿った並べ）と、接続表で見せる。承認の記録（日付・承認された版の hash／ファイル）を Issue に残す。承認後にモックを変えたら再承認が要る。
3. **原文の形語彙を機械導出で置換しない。** 原文に『斜め』『一本道』『右上』等の形・方位語があるMAPは、その語を割付図でそのまま実現し、機械導出で別の形（L字・直線）にしない。モックには、原文の形語彙と1行ずつ照合した表を添える。導出が必要な未決は『仮案』と明記して見せ、承認を得る。
4. **土台縁・机・遷移範囲**: モックには土台縁と机の余白を必須で載せる。通路は画像端でなく模型の縁まで届かせ、遷移は辺上の範囲指定にする。画像全面ベタの割付図は禁止。
5. **並行生成の条件**: 『モック承認済み＋代表1枚を kako-jun が見て承認済み』のときだけ許可する。
6. **保留MAP（原文未確定）**: 形を発明しない。モックには『未確定』枠で載せ、kako-jun に決めてもらう。
7. 違反例（2026-10-22 体内）: 手足を L字・縦直線のモックのまま BDY-10 を試験生成し、12枚の並行生成まで進めた。『斜めに伸びる道でないと』と却下された。

## 他の絶対ゲート（全文は `gates.md`。要点だけここに置く）

- **一意解釈ゲート**: `少し`・`やや`・`広い`・`自然`・`斜め`だけ等の曖昧語で形・幅・方角を決めない。道・水路・建物の形を直線・直交・格子へ正規化しない。根拠がなければ TBD を残して停止し、数値を発明しない。
- **材料固定宣言**: 「手作り」「模型」だけで生成しない。各生成入力に対象ごとの材料・道具・接着方法を列挙し、原寸で三つ以上確認できなければ `failed`。
- **台帳原文ゲート**（寺町など `docs/ledger/MAP.yaml` に行があるMAPは台帳が正本で、決定・未決・窓・採用要素は `oblique_build.py` が全件プロンプトに入れる。以下は台帳に行が無いエリア用）: 対象MAPの台帳原文（registry・specifications・topology・checklist・再構築候補台帳）を**要約せず逐語で**生成入力に添付する。読めない・矛盾する・接続相手の原文が確認できないなら `blocked`。生成直前に原文→prompt の対応を照合する。
- **建築連続性ゲート**: 複数MAPが一建物を表すエリア（寺・学校・住宅）は、建築不変表を転記し、外観参照を先に通す。
- **接続は接続表だけで判定**する。通路は模型の縁まで。必須接続を先に固定し、行き止まりは後。

## エリアを1つ作る標準手順（12工程）

エリア＝台帳の区域コード1つ（例 BDY、TRM。MAP は 2桁連番）。**工程を飛ばさない。順序を入れ替えない。** 各工程の「やってはいけないこと」は過去の手戻りの実例（体内 = 2026-10-22〜23、`pitfalls.md`）。

### 0. 着手前の確認票（kako-jun にまとめて聞く）

- 入力: エリアの台帳原文、`docs/map-topology.md` の接続、過去エリアの決定。
- 出力: **Issue**（`issue-template.md` の本文で新規作成）。確認票の全項目に、kako-jun の回答を**逐語で**記録する。
- 合格条件: 確認票の全項目が『回答済み』か『既定案で進めてよいと明示された』になっている。未決の形（原文にない部屋・MAP）は『未確定』として残し、先へ進める範囲を明記する。
- ツール: なし（`gh issue create`）。
- やってはいけないこと: 質問を途中で小出しにする（体内の手戻りの大半は、途中で直された項目＝ここで聞けた）。既定案で黙って進める。質問に「推奨で」と返されたら、その決定を逐語で Issue に書く。

### 1. 原文束と形語彙の照合

- 入力: 台帳原文（`gates.md` の台帳原文ゲートの5種）、工程0の回答。
- 出力: 原文束（逐語）と、**原文の形・方位語 → モックでの実現**の1行ずつの照合表。
- 合格条件: 形・方位語（斜め・一本道・右上・左右など）が全て、工程0で決めた約束（左右の基準・北上固定など）と矛盾なく割付図へ落ちる表になっている。未決は『仮案』と書く。
- ツール: `grep`／台帳を Read。体内は `build_body_prompt.py` の `build_bundle`。
- やってはいけないこと: 原文を要約・言い換え・補完する。body.svg 等の図から機械導出した形で原文の形語彙を置き換える（体内: 手足を L字にした）。docs を更新して原文行を変えたあと、prompt の逐語照合を再実行しない（`pitfalls.md` 『docs 更新が逐語照合を壊す』）。

### 2. モック（幾何をコードで作る）

- 入力: 工程1の照合表と約束（左右・道幅・遷移範囲）。
- 出力: 全MAPの割付図（clean ＝ 清書用・通常 ＝ 注記つき）と一覧画像（地図／体の配置に沿った並べ）と接続表。画素は 1920×1080。
- 合格条件: **模型の天面が画像の内側に収まり、外周に机→土台の縁→天面が見える**。通路は画像端でなく模型の縁まで届く。遷移は辺上の範囲指定。接続の両端が反対の辺で、余分な通路が無い（機械検査）。道幅は工程0で決めた基準（キャラ何人分）。
- ツール: 体内は `tools/body_layout.py`（`--clean` で清書用）、`body_sheet.py`（一覧）、`body_geometry_json.py`（幾何JSON）、`body_step_scan.py`（斜めの帯の段差検査）。**新エリアは `body_layout.py` の作り直しが要る**（`tools/README.md` の『次にやること』）。
- やってはいけないこと: 画像全面ベタの割付図。曲がりや分岐を機械導出の都合で変える。手足の帯に段差（Z形）を残す。

### 3. モック提示ゲート（全MAPのモックを見せて承認）

- 入力: 工程2の一覧・接続表・照合表。
- 出力: kako-jun の明示承認。Issue に『承認済みモックの記録』（日付・MAPごとの clean と通常の sha256）。
- 合格条件: 全MAPが承認済みか『未確定』枠。承認後にモックを変えたら再承認。
- ツール: `sha256sum`、`gh issue comment`。
- やってはいけないこと: 本ゲートの全項目（冒頭）。「試験だから1枚だけ」。レビューや機械検査の通過を承認の代わりにする。

### 4. prompt を機械生成（原文束逐語・装飾・参照2枚）

- 入力: 承認済みの clean 割付図、原文束、装飾計画。
- 出力: MAPごとに `*-prompt.md`（来歴・照合表・実測）と `*-prompt-send.txt`（そのまま送る文）。送信文＝wrapper → SOURCE TEXT（逐語）→ WHAT TO DRAW（構造＋装飾を1回で）→ REFERENCE（**参照2枚だけ**: clean 割付図＋材料見本）。
- 合格条件: 座標・幅・曲がりは clean **画素の実測**で書かれ、本文と原文の逐語照合が0件不一致。禁止モチーフ語が自作部分に無い（肯定形で書く）。送信文が文字数上限内。赤紙などの定数アクセントの数と置き場が文言に入っている。
- ツール: 体内は `tools/build_body_prompt.py`（`--verify-send`・`--verify-bundle`・`--plan`）。**新エリアはビルダーの部品分離が要る**（`tools/README.md`）。
- やってはいけないこと: 様式参照画像を渡す（幾何が崩れる）。簡素な背景を先に作る2段階生成。禁止語を書いて避けさせる（逆に描かれる）。装飾を全MAP同じ組み合わせにする（MAPごとに変え、隣接で被らせない）。原文の語（『分岐室』『洞窟口』）が指示と誤読される箇所を放置する。参照を古いコピーで渡す。

### 5. 独立レビュー（生成前 prompt）

- 入力: **送信予定の完全 prompt**、参照2枚の実画素、原文束。
- 出力: `docs/reviews/artifact-redteam/` のレビュー文書（ステージ宣言 `contract/prompt`、版の sha256）。
- 合格条件: blocker・major 0。指摘は全件修正して**再レビュー**（小さな修正でも省かない）。
- ツール: `sit-artifact-redteam`（作成者でない担当。サブエージェントはメイン以下のモデル。メインがSonnetなら sonnet 以下）。
- やってはいけないこと: 作成者が自分でレビューする。要約だけを渡す。修正後の再レビューを省く。

### 6. 代表1枚を生成して見せる

- 入力: 承認済みモック、レビュー通過の送信文、現行ファイルから作った参照コピー（sha256 照合済み）。
- 出力: 1枚の生成画像（返却原本を無加工で保存）、チェッカー結果、重ね画像、**kako-jun に画像を直接見せる**。
- 合格条件: 実寸が 1920×1080 または 1672×941、`check_body_image` 相当のチェックと目視を通り、kako-jun が『よい』。
- ツール: `codex exec --skip-git-repo-check -s workspace-write -i ref1.png -i ref2.png < send.txt`（**`--full-auto` は不可**）。保存失敗は `pitfalls.md` の回収手順。
- やってはいけないこと: 承認前の生成。自動の再生成（kako-jun が求めたときだけ）。代表を選ぶのに難しいMAP（迷路など）を避ける——代表は**型の異なるMAP**（直線・曲がり・分岐・部屋）から選び、難しい型だけ複数枚見せる。

### 7. 承認後に並行生成

- 入力: 工程6の承認。
- 出力: 残りのMAPの生成画像（1MAPあたり原則1回。再生成は kako-jun が求めたときだけ）。
- 合格条件: 作業ファイル名が MAP・担当ごとに固有（`pitfalls.md`）。参照コピーが sha256 照合済み。
- ツール: 工程6と同じ。担当ごとに scratchpad の作業ディレクトリを分ける。
- やってはいけないこと: 共有ファイル名（`send.txt`・`ref1.png`）の使い回し。他人のプロセスを kill する。承認前の並行。

### 8. チェッカーと目視

- 入力: 生成画像、clean 割付図。
- 出力: MAPごとの実測（寸法・床IoU・土台縁4層・通路・赤紙の枚数/模型外・装飾の色域）と半透明の重ね画像、採否一覧。
- 合格条件: 寸法ゲート。FAIL は原因を目視で切り分け（誤判定か本当の崩れか）、WARN は重ね画像を目視。**採否は kako-jun の目視**。
- ツール: `check_body_image.py`、`body_floor_overlay.py`。
- やってはいけないこと: チェッカーの合否を美観の判定にする。『かなりいい』と言われた後の作り直し（編集元を固定した装飾追加の1回だけ。床IoUで幾何不変を確認）。

### 9. 基準状態の採用（保存・来歴・台帳・Issue）

- 注: ここでの採用は基準状態の画像の保存・来歴の記録で、マスク（工程10）の前でよい。台帳の `ready` 化はマスクと red-team（工程11）の後。
- 入力: kako-jun が採用した画像。
- 出力: 正本パスへの保存（WebP q85。MAP ID の正本名）、採用記録（送信文・参照・測定値・sha256・既知の逸脱）、台帳の更新、Issue コメント。
- 合格条件: 保存画像の実寸・sha256 を測り直して記録した。不採用・失敗画像は残さず削除（来歴だけ記録）。使う可能性のあるテイクは**次を生成する前にコミット**。
- ツール: `magick`、`sha256sum`、`git add <名指し>`。
- やってはいけないこと: 候補置き場・版suffix。寸法が1px違う（1672×940）のをリサイズして通す——**例外は kako-jun の承認＋記録**（体内 BDY-13）。承認済みの逸脱は台帳・採用記録・Issue の3か所に書く。

### 10. 位置合わせ・マスク

- 入力: 採用画像、clean 割付図、幾何JSON。
- 出力: マスク（可逆WebP）・出口候補 links・register（床の差・位相・信頼度）。
- 合格条件・手順: `../sit-field-mask/SKILL.md` の共通手順（位置合わせ→床色基準の切り出し→出口の喉→禁止辺）。
- ツール: 体内は `body_register.py`→`body_mask_export.py`。
- やってはいけないこと: マスクの真実を割付図にする（**画像の床の見えが正**）。影で暗い床を黙って black にする（定義して記録）。

### 11. red-team（マスク・採用）

- 入力: 採用画像・マスク一式の**版（sha256）**、台帳、links。
- 出力: `docs/reviews/artifact-redteam/{日付}-{エリア}-masks-redteam-*.md`（第1回）と `-r2`（第2回）。
- 合格条件: blocker・major 0（承認済みの逸脱は『承認済み』と明記）。第2回で**退行がない**ことを確認。
- ツール: `sit-artifact-redteam`（作成者でない担当）。
- やってはいけないこと: 作成者の自己評価を根拠にする。第2回を省く。

### 12. コミット・push

- 入力: 変更したファイルだけ。
- 出力: 日本語の `docs: ` 流儀のコミット、`git push origin <現ブランチ>`。PR は kako-jun が決めたタイミング（工程0の回答）で作る。
- 合格条件: `git diff --cached` に**そのエリアのハンクだけ**がある。
- ツール: `git add <名指し>`／別セッションの変更が同じファイルに混ざるときは `git add -p`（対象ハンクだけ）。
- やってはいけないこと: `git add -A`・`git stash`・`reset --hard`・force push・main への直接 push。Co-Authored-By やAI痕跡をコミットに付ける。`--no-verify`。

## 目標の見た目と共通の約束（要点。全文は `gates.md`）

- 写真に見えてはいけない。身近な材料で無理やり再現した手作りの模型。**土台の板（foamboard＋corrugated 断面）とまわりの机が見えたまま**。真上寄りの俯瞰。空・地平線・消失点・人物・文字なし。
- 机は木目にする（エリアで変えない）。装飾密度は寺町の幼稚園（TRM-02採用画像）級。装飾は地形・縁・机にだけ置き、歩く床は空ける。
- 通路的な背景（道だけの絵）は1つの町につきせいぜい1つ。残りは場所の個性を持たせる。

## 禁止事項

- Co-Authored-By をコミットメッセージに付けない
- `--no-verify` を使わない
- 生成画像について、独自に性的・不適切の判定をして削除・停止しない（そのまま報告する）
- 指示されていない再生成をしない
- `python3` の直接実行をしない（`uv run python3`）
- 台帳原文を要約した指示だけで生成しない
- 原文にない建物間の外部接続・別棟・渡り廊下・出口を作らない

### 決定（kako-jun、2026-10-23）

- **全体レビューが承認ゲートの核**: 各戸口の位置・向き・幅（`width_class`: 原則キャラ2人分・住居/幼稚園の外への戸口1.5人分・勝手口1人分）・相手 MAP の戸口との位置整合・寺町外への端点を載せた接続図（白黒ワイヤー。昔の攻略本流）と全MAP一覧を見せ、通ってから生成する。生成後の修正より、モック段階の接続修正を優先する。
